# What is the Iru platform (formerly Kandji), its core products and architecture (endpoint management, identity, security/EDR, compliance), how it differs from Jamf, and what systems administrators need to know when an organization is transitioning to it?

## Answer

Iru is the renamed Kandji platform: separately licensed Endpoint Management, Endpoint Detection & Response, Vulnerability Management, Workforce Identity, and Compliance automation in one tenant. Endpoint operations assign each device to one Blueprint, deploy Library Items through Apple or Windows MDM plus a Mac/Windows agent, and vary payloads with Assignment Map rules. Compared with Jamf Pro 11.33.0, a move is a re-enrollment and a scope redesign; the documented Iru upgrade keeps an existing Kandji tenant and does not import Jamf Pro policies or smart groups.

## Findings

- Kandji is now Iru. The product list is Endpoint Management (Apple, Windows, Android), Endpoint Detection & Response (Mac and Windows), Vulnerability Management (Mac and Windows), Workforce Identity, Iru AI, Compliance Automation, and Trust Center. Identity areas may vary by subscription. — [T2] Iru Overview (https://docs.iru.com/en/iru/platform-overview/iru-overview)
- Billing rows are the public license gates: Device Management split by macOS, Windows, Android, and Mobile; EDR by platform; Vulnerability Management by platform; Compliance items such as ISO 27001, SOC 2, Trust Center, and Seats; Identity as monthly active users. Plan changes go through Contact sales. A child tenant’s billing is handled by the MSP parent. — [T2] Billing Page (https://docs.iru.com/en/iru/platform-overview/billing-page)
- The overview’s “single agent” across Apple, Windows, and Android conflicts with the operational docs. Those docs put a proprietary agent on Mac and Windows only. iPhone, iPad, Apple TV, and Vision check in through MDM. Android reports state through the Android Management API and Google Pub/Sub. The operational docs are the architecture to plan against. — [T2] Iru Overview (https://docs.iru.com/en/iru/platform-overview/iru-overview); [T2] Iru Agent and MDM (https://docs.iru.com/en/endpoint/agent/iru-agent-and-mdm); [T2] Device Check In (https://docs.iru.com/en/endpoint/devices/device-check-in/device-check-in)
- On a Mac, MDM (via APNs) enrolls the device, installs the agent with `InstallEnterpriseApplication`, delivers configuration profiles, Apps and Books, and device commands. The Swift agent, plus a system extension on Apple’s Endpoint Security framework, enforces Parameters, runs scripts as root, installs Auto Apps, Custom Apps, and Custom Printers, and runs EDR and Vulnerability Management scans. If MDM has checked in within 7 days and the agent has not, MDM reinstalls the agent. — [T2] Iru Agent and MDM (https://docs.iru.com/en/endpoint/agent/iru-agent-and-mdm)
- Mac agent check-in is every 15 minutes (agent update, Parameters, pending Library Items) and every 24 hours (those items plus daily scripts, compliance scripts, inventory). Item order is Custom Scripts (1 hour each), Custom Printers (3 hours), Custom Apps (12-hour global limit), Auto Apps (6 hours), Managed OS (12-hour global limit), alphanumeric within a type. MDM commands and profiles have no fixed interval. Daily MDM inventory is a separate 24-hour command set (`ProfileList`, `InstalledApplicationsList`, `SecurityInfo`, `CertificateList`, `AvailableOSUpdates`, `DeviceInformation`). `sudo iru run` forces the agent loop; Perform daily check-in does not. — [T2] Device Check In (https://docs.iru.com/en/endpoint/devices/device-check-in/device-check-in)
- Windows management is Windows MDM plus the agent. The agent, every 15 minutes, does app inventory, Auto Apps, Custom Apps (MSI/EXE in a zip), and PowerShell. New MDM policies go out through WNS and generally apply within a couple of minutes on an online device. User drift, such as a local firewall change, is remediated on the 24-hour MDM check-in. Perform daily check-in pushes policies that were waiting; it does not remediate policies already applied and does not sync the agent. Initial enrollment needs a local administrator. — [T2] Iru Agent and MDM (https://docs.iru.com/en/endpoint/agent/iru-agent-and-mdm); [T2] Device Check In (https://docs.iru.com/en/endpoint/devices/device-check-in/device-check-in); [T2] Device Requirements (https://docs.iru.com/en/iru/requirements/device-requirements)
- Supported OS, as of the requirements page: macOS Golden Gate 27, Tahoe 26, and Sequoia 15; iOS, iPadOS, and tvOS 18 or later; visionOS 2 or later. Intel Macs are supported through Tahoe 26. Virtualized Macs and cloned images of an already enrolled Mac are unsupported. Sonoma 14 and iOS/iPadOS/tvOS 17 reached end of support on 2026-10-15 (no new fixes) and reach end of life for enrollment on 2027-01-13. Ventura 13 and Apple 16-and-earlier are already unable to enroll. Windows is 11 24H2, 25H2, 26H1, or 26H2 on Pro, Pro Education, Enterprise, or Education; VMs need a defined serial. Android is 14+ on Android Enterprise with Play services; Android 13 is end of support. — [T2] Device Requirements (https://docs.iru.com/en/iru/requirements/device-requirements)
- A device is assigned to one Blueprint. Moving it makes the destination Blueprint the source of Library Items and Parameters. On Mac, Parameters and other agent items change at the next agent check-in; profiles and Apps and Books apps are added or removed at the next MDM check-in; enforced Auto Apps and Custom Apps are not removed. On Windows, apps already installed remain; settings change only if the new Blueprint’s policies change them. On iPhone, iPad, Apple TV, and Vision, Library Items are added or removed at the next MDM check-in. On Android, items no longer assigned are updated or removed through Google’s channel. — [T2] Moving Devices Between Blueprints (https://docs.iru.com/en/endpoint/blueprints/assignment-maps/moving-devices-between-blueprints)
- Classic Blueprints were converted to Assignment Maps on 2026-04-01. Inside a map, each conditional block is first-match, then the next block is evaluated, so several blocks can apply. Rules can use device family, enrollment type, chip, FileVault, supervision, Mac family, asset tag, serial, OS version, tags, user department, email, username, job title, and user group. Some of those are Apple-only. Editing a map reevaluates rules immediately. A device lookup shows the path through the map. Individual devices can be excluded from one Library Item. Blueprint Routing uses the same style of rules, first match, and only at enrollment; ongoing changes stay in the Assignment Map. The ADE Library Item is outside conditional logic. — [T2] Using Conditional Logic in Blueprints (https://docs.iru.com/en/endpoint/blueprints/assignment-maps/using-conditional-logic-in-blueprints); [T2] Blueprint Routing (https://docs.iru.com/en/endpoint/enrollment/blueprint-routing)
- EDR is an add-on, deployed as a Blueprint Library Item. On Mac it uses Endpoint Security for file and behavioral detection, independent Detect or Protect posture for malware, PUPs, and malicious behavior, process termination, quarantine, hash or path allow and block lists, and device isolation. On Windows it is file-based Detect mode only (no automatic quarantine), Intel or AMD x64, Windows 11 24H2, 25H2, or 26H2. Windows 11 26H1 and Arm are outside Windows EDR. The same add-on is required for the Accessory & Storage Access Library Item even when the EDR Library Item is not assigned. — [T2] Endpoint Detection & Response (EDR) Overview (https://docs.iru.com/en/endpoint/endpoint-detection-response-edr/endpoint-detection-and-response-edr-overview)
- Vulnerability Management is its own licensed product. On Mac, scans run in the agent. The overview places the product on Mac and Windows; this pass did not read a Vulnerability Management configuration page, so remediation behavior is unresolved. — [T2] Billing Page (https://docs.iru.com/en/iru/platform-overview/billing-page); [T2] Iru Agent and MDM (https://docs.iru.com/en/endpoint/agent/iru-agent-and-mdm); [T2] Iru Overview (https://docs.iru.com/en/iru/platform-overview/iru-overview)
- Iru Identity is a separate workforce identity product: it can be the IdP (passkey or Iru Access app, SAML and OIDC apps), holds a directory and groups, provisions from HR or a file, and adds device-trust conditions on top of the authenticator. Google, Microsoft Entra ID, SAML, and OIDC connections can front sign-in. Features move through release stages, and early ones are marked on the page. This pass did not read the system-architecture page, so the device-trust data path is unresolved. — [T2] Iru Identity overview (https://docs.iru.com/en/identity/getting-started/overview)
- Iru Compliance is framework evidence (controls, actions, artifacts, sources), not an MDM compliance smart group. Documented catalogs include SOC 2, ISO 27001, ISO 42001, and HIPAA; others appear when the tenant has them. Trust Center publishing depends on the plan. Endpoint can be a read-only evidence source. The endpoint UI also says “device compliance status”; this pass did not read a page that defines that status. — [T2] Getting Started with Compliance (https://docs.iru.com/en/compliance/getting-started-with-compliance); [T2] Billing Page (https://docs.iru.com/en/iru/platform-overview/billing-page)
- Jamf Pro 11.33.0 enrolls Apple devices by Automated Device Enrollment (the method that can prevent removal of the MDM profile), Device Enrollment (profile-driven or account-driven), or account-driven User Enrollment for personally owned devices. Policies on computers have their own scope, execution frequency, and trigger, and can be offered in Self Service. Removing a target from a policy’s scope does not remove settings that policy already applied. The built-in Update Inventory policy submits inventory weekly by default. Smart groups for computers, mobile devices, or users recalculate from inventory criteria and are what Jamf recommends for scoping; nested groups are called out as a server-performance risk. Computer configuration profiles are computer-level or user-level, installed automatically or via Self Service; user-level profiles may wait for logout or restart. The fetched profile page does not say whether a profile is removed when scope is lost. — [T2] Enrollment (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Enrollment_into_Jamf_MDM); [T2] Policies (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Policies); [T2] Smart Groups (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Smart_Groups); [T2] Computer Configuration Profiles (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Computer_Configuration_Profiles)
- Enrollment troubleshooting tells admins to check that the device is not already in another MDM, and to remove it from Apple Business or Apple School Manager if it was previously enrolled elsewhere. No fetched Iru page describes importing Jamf Pro policies, packages, extension attributes, or smart groups. — [T2] Device Requirements (https://docs.iru.com/en/iru/requirements/device-requirements)
- Upgrade to Iru is the Kandji-tenant cutover, deadline 2026-12-01. Devices, configurations, and data stay. The tenant moves to `{{subdomain}}.iru.com`, sessions end, Standard Authentication becomes a passkey, and SAML, Google, and Microsoft connections must be recreated (new ACS, redirect, SSO, and entity IDs). End users are not asked to re-enroll; the enrollment host becomes `{{subdomain}}.iru.com/enroll`. An AD CS connector on Windows Server is a separate post-upgrade install. That workflow does not apply to a Jamf Pro fleet. — [T2] Upgrade to Iru (https://docs.iru.com/en/iru/platform-overview/upgrade-to-iru)
- After the 2026-04-08 brand update, user-facing names are Iru Agent and Iru Self Service. New Self Service links use `iru-self-service://`; `kandji-self-service://` still works. Unified Logging, some bundle IDs, launchd labels, and on-disk paths stay `io.kandji` or Kandji-prefixed. Windows agent logs remain `%ProgramData%\kandji\agent\logs`. Migrated tenants can call `https://subdomain.api.kandji.io/api/v1` or `https://subdomain.api.iru.com/api/v1`. — [T2] Iru Brand Update (https://docs.iru.com/en/iru/platform-overview/iru-brand-update); [T2] Iru Agent and MDM (https://docs.iru.com/en/endpoint/agent/iru-agent-and-mdm)
- The Endpoint Management API is JSON over bearer tokens. The reference documents US `https://SubDomain.api.kandji.io` and EU `https://SubDomain.api.eu.kandji.io`, and a limit of 10,000 requests per hour per customer. It does not list `api.iru.com`. Tokens are created in Access, scoped per route, shown once, and shared across that one hourly limit. Deleting the team member who created a token deletes the token. Compliance evidence calls count toward the same limit. — [T1] Iru Endpoint Management API (https://api-docs.iru.com/); [T2] Iru API Overview (https://docs.iru.com/en/endpoint/api/iru-api-overview); [T2] Iru Brand Update (https://docs.iru.com/en/iru/platform-overview/iru-brand-update)

## Recommendation

Treat a Jamf Pro move as a new enrollment and a new scope design: a few Blueprints, Assignment Map rules for the exceptions that used to be extra smart groups, and a pilot that measures Mac Blueprint moves before a wide cutover, because enforced Auto Apps and Custom Apps stay installed. Confirm EDR, Vulnerability Management, Identity, and Compliance on the Billing page before planning those workstreams; Windows EDR, if licensed, reports and does not quarantine. The tradeoff is one assignment container and a fixed 15-minute agent loop, against Jamf Pro policies that each have their own trigger and frequency and that leave prior settings in place when scope is removed.
