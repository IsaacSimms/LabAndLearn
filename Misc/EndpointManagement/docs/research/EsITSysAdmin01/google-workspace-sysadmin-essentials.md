# What are the core Google Workspace admin concepts, tools, and troubleshooting patterns an IT Systems Administrator needs for enterprise escalation work (Admin console, directory/users/groups, shared drives, security & compliance controls, common Okta/IdP integration points, and frequent failure modes)?

## Answer

Google Workspace keeps its own directory when Okta or another IdP does single sign-on: each user has one primary email, one organizational unit, and a license, and service settings inherit down that unit until a higher-priority configuration group or an access group overrides them. Escalation is a four-layer check — Okta app assignment and provisioning, the Google SSO profile on that unit or group, the account's license and lifecycle state, and a service control that can deny access after sharing looks correct. Super admins are a separate sign-in path: newer SSO profiles do not do super-admin SSO, and `admin.google.com` expects the Google password.

## Findings

- The Admin console is at `admin.google.com`. The surfaces that show up on escalation are Directory (Users, Groups, Organizational units), Apps (Drive and Docs), Security (Authentication, API controls, Alert center, Security center), Reporting (audit and investigation), Billing (licenses), and Admin roles. — [T2] [Admin console map](https://support.google.com/a/answer/55955?hl=en)
- A missing menu is often a missing privilege. SSO profile work needs Security Settings. Shared-drive membership in the console needs Drive & Docs. The user list needs User management. The security investigation tool needs Security center. Restore of a deleted user, unmanaged-account invites, transfer of ownership during deletion, domain-wide delegation, and changes to other admins are super-admin tasks. A User Management Admin can create and delete non-admin users and cannot change an administrator account. Google recommends at least two super admins. — [T2] [Prebuilt administrator roles](https://support.google.com/a/answer/2405986?hl=en), [Troubleshoot shared drives](https://support.google.com/a/answer/7337638?hl=en), [Setting up SSO](https://knowledge.workspace.google.com/admin/apps/setting-up-sso)
- Each user is in exactly one organizational unit. Children inherit until they override. The top unit's path is `/`. Putting a user in a different unit changes which Workspace services they can use. Google's own setup guidance is to keep user units and device units separate. — [T2] [How the organizational structure works](https://support.google.com/a/answer/4352075?hl=en) — [T1] [Directory API users `orgUnitPath`](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users), [Directory API orgunits](https://developers.google.com/workspace/admin/directory/reference/rest/v1/orgunits)
- The Directory user record is the identity Okta has to match. `primaryEmail` is required, unique, and cannot be another user's alias. `isAdmin` (super admin) is output-only on insert and update; only `makeAdmin` sets it. `suspended`, `suspensionReason`, `archived`, `deletionTime`, `aliases`, and `orgUnitPath` are on the same resource. — [T1] [Directory API users](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users)
- Configuration groups are the exception layer on top of units. A user's group setting overrides the unit. Membership can span units, and a user can be in several configuration groups; the highest-priority group wins and settings are not merged. Priority is edited only in the Admin console. Eligible groups are created in the Admin console, the Directory API, or Google Cloud Directory Sync. Groups created in the Google Groups app cannot be configuration groups. A dynamic group needs the security label. Search by the group's email address. The Users view on a setting shows which group or unit actually won; the unit's own Inherited/Overridden flag ignores groups. Apply can take up to 24 hours. A 2-Step Verification policy on the user's child unit beats a configuration-group exemption. — [T2] [Customize service settings using configuration groups](https://support.google.com/a/answer/9224126?hl=en) (last updated 2026-10-26 UTC)
- Access groups turn a service on for members and override a unit that has the service off. They leave an already-on service on. They do not assign licenses. The same group can be both an access group and a configuration group. — [T2] [Customize service access using access groups](https://support.google.com/a/answer/9050643?hl=en)
- Licenses are per user and gate features inside a unit that already has the setting. One Workspace license covers the included apps. Multiple subscriptions require assignment. Automatic licensing can be on for only one service or subscription, can take up to 24 hours, and while it is on for everyone an individual license cannot be removed. A license assigned to a unit flows to child units unless the child overrides. On a configuration group, a flag can appear beside a setting the edition does not include, whether or not the group contains an unlicensed user. — [T2] [How licensing works](https://support.google.com/a/answer/6309862), [Assign, remove, and reassign licenses](https://support.google.com/a/answer/1727173?hl=en), [Configuration groups](https://support.google.com/a/answer/9224126?hl=en)
- Suspend blocks Google Workspace sign-in and new mail and calendar invitations. Data stays. Collaborators keep shared documents. The active license is still billed. An admin can restore the account later. If Google suspended the account, mail delivery can continue. — [T2] [Suspend a user temporarily](https://support.google.com/a/answer/33312)
- Archive assigns an Archived User license, blocks sign-in on any system, hides the user from the Global Address List, and frees the active license within 24 hours. Data remains. Vault retention and holds apply when the user has a Vault license or an Archived User subscription that includes Vault. Business Plus, Enterprise Standard, and Enterprise Plus can buy that subscription in the console. An archived user can be deleted or unarchived, and the console will not suspend them. Unarchive needs a free license of the same edition, then a manual Workspace license assignment. — [T2] [Archive former employee accounts](https://support.google.com/a/answer/9048836?hl=en), [Preserve data for users who leave](https://support.google.com/vault/answer/2736622?hl=en)
- Delete on a domain-verified account removes access and user-owned data. Gmail, untransferred Drive files the user owns, and the primary calendar can be restored for 20 days by a super admin if a matching license is free. Restore usually takes up to 24 hours and can take up to 5 days. The address can be given to another managed user during those 20 days and is removed from Workspace after 20 days. Using it for an unmanaged personal account waits 30 days. Shared-drive files stay, because the organization owns them. Groups the user created stay. A failed data transfer stops the delete and leaves the data in place. Vault retention and holds stop applying at delete, and that data can be purged immediately, including after a restore inside 20 days. A user on litigation hold cannot be deleted until a Vault admin lifts the hold, which can take up to 48 hours. Do not delete to clear a conflicting account, to rename a user, to block them temporarily, or to save a license. — [T2] [Delete or remove a user](https://support.google.com/a/answer/33314?hl=en) (last updated 2026-10-26 UTC), [Restore a recently deleted user](https://support.google.com/a/answer/1397578?hl=en), [Vault: preserve data](https://support.google.com/vault/answer/2736622?hl=en)
- A conflicting account is an unmanaged consumer account with the same primary email. Aliases are out of scope for the Transfer tool and for Conflicting accounts management. That setting applies when accounts are created with the Admin SDK Directory API. Only a super admin manages it. — [T2] [Find and add unmanaged users](https://support.google.com/a/answer/11112794?hl=en)
- Shared-drive create and member management are edition-gated. The admin troubleshoot list is Business Standard and Business Plus; Enterprise Standard and Enterprise Plus; Education Fundamentals, Education Standard, and Education Plus; Essentials, Enterprise Essentials, and Enterprise Essentials Plus; Nonprofits; G Suite Business. A Business Starter shared-drive manager can only reset sharing to allow-all. Both Enterprise editions include shared drives, Drive trust rules, Drive DLP, and advanced Drive sharing. Client-side encryption for Drive files is Enterprise Plus. — [T2] [Troubleshoot shared drives](https://support.google.com/a/answer/7337638?hl=en) (last updated 2026-10-26 UTC), [Compare Enterprise editions](https://knowledge.workspace.google.com/admin/getting-started/editions/compare-enterprise-editions)
- "Cannot create a shared drive" is the user's license, or shared-drive creation unchecked on their unit with no configuration-group override. "Manager cannot change sharing" is the same license list, or "Allow members with manager access to override the settings below" unchecked for their unit or configuration group. A drive with no manager can have members changed only in Apps > Google Workspace > Drive and Docs > Manage shared drives. A drive with no members exposes files only through direct shares. — [T2] [Troubleshoot shared drives](https://support.google.com/a/answer/7337638?hl=en)
- Membership does not guarantee access. Drive sharing settings, trust rules, and DLP override the drive and the file. Shared drives are themselves assigned to a unit (top unit by default). That unit's sharing, DLP, storage, and data-region policies apply to the drive, separate from the member's user unit. — [T2] [Troubleshoot shared drives](https://support.google.com/a/answer/7337638?hl=en), [Manage data policies for specific shared drives](https://support.google.com/a/answer/7337635)
- Access levels are Manager, Content manager, Contributor, Commenter, and Viewer. Every member can view every item unless a Manager limits a folder. Only Managers add or remove members, change levels, permanently delete trash, or delete the drive. Content managers can move items to the trash; Contributors cannot. In Drive for desktop and the ChromeOS Files app, Contributor is read-only; create, upload, and edit there need Content manager or Manager. Removing a member also removes direct shares of items inside that drive. A file moved in keeps direct shares, drops inherited folder shares, and the person who created it is no longer the owner. — [T2] [How file access works in shared drives](https://support.google.com/a/users/answer/12380484?hl=en)
- A shared drive holds at most 500,000 files, folders, and shortcuts. A folder move that would pass that limit fails. — [T2] [Troubleshoot shared drives](https://support.google.com/a/answer/7337638?hl=en)
- Two Google documents disagree on who can move a folder. The admin troubleshoot page says a move into a shared drive needs at least Contributor on the destination plus Editor or Owner on the source, and a move out of or between drives needs Manager on the source and at least Content manager on the destination. It maps `insufficientFilePermissions` (403) to missing Manager on the source drive. The Learning Center says a folder move into or between shared drives needs Manager on both the original and the target. Treat the 403 and the current membership as the facts on the ticket, and do not pick one matrix as universal. — [T2] [Troubleshoot shared drives](https://support.google.com/a/answer/7337638?hl=en), [How file access works in shared drives](https://support.google.com/a/users/answer/12380484?hl=en)
- Google is the service provider for third-party SSO. Profiles live at Security > Authentication > SSO with third party IdP. SAML and OIDC are both supported, including a preconfigured Microsoft Entra OIDC profile. An organization can hold up to 1,000 SAML profiles. Assignment is to a unit or a group, never to one user; the Users view shows the effective profile. A group assignment overrides the unit. Among groups, list order wins, top to bottom, and a nested child inherits its parent unless a higher-priority group also matches. Choosing None turns SSO off for that unit or group. Saves can take up to 24 hours. — [T2] [Setting up SSO](https://knowledge.workspace.google.com/admin/apps/setting-up-sso)
- A SAML profile needs the IdP entity ID, sign-in URL, sign-out URL, change-password URL, and an X.509 PEM or DER certificate whose public key is DSA or RSA and matches the signing key. Two IdP certificates can be stored for rotation. The ACS URL and Entity ID are unique per profile and are what the IdP must be given. For OIDC, the IdP `email` claim must equal the user's Google primary email, and the IdP must use the authorization-code flow. — [T2] [Setting up SSO](https://knowledge.workspace.google.com/admin/apps/setting-up-sso)
- The legacy SSO profile is the single-IdP profile with network masks and an optional domain-specific issuer (`google.com/a/<primary-domain>` versus `google.com`). Masks limit which client IPs are sent to the IdP. Newer profiles replace that with unit and group assignment. If the legacy profile is still enabled, Google accepts assertions posted to the legacy ACS URL and checks them with the legacy certificate even when that user is a super admin or is assigned a different SAML profile. — [T2] [Setting up SSO](https://knowledge.workspace.google.com/admin/apps/setting-up-sso)
- Newer SSO profiles do not support super-admin SSO. On the legacy profile, super-admin SSO works for IdP-initiated sign-in, for domain-specific service URLs set to redirect to the IdP, and for a non-super Google sign-in that then asserts the super-admin identity at the IdP. Super admins opening `admin.google.com` enter their full Google administrator email and Google password. The Drive sync client sign-in for a super admin also stays on Google. Okta documents the same `admin.google.com` password path, plus `https://www.google.com/a/[DOMAIN]`, and tells you to keep a super admin that can sign in when SAML is broken. — [T2] [Super administrator SSO](https://support.google.com/a/answer/6341409?hl=en), [Okta SAML 2.0 for Google Workspace](https://saml-doc.okta.com/SAML_Docs/How-to-Enable-SAML-2.0-in-Google-Apps.html)
- The SAML sign-out URL is the page the user lands on after leaving a Google app. The change-password URL is where non-super-admins are sent from `https://myaccount.google.com/` instead of changing a Google password. On the legacy profile that redirect applies even outside the network masks, and it applies even when SSO is not enabled; clear it when SSO and password sync are both off. If a SAML profile's sign-in option requires the Google username and password, that profile's change-password URL is ignored. — [T2] [Setting up SSO](https://knowledge.workspace.google.com/admin/apps/setting-up-sso)
- Okta's Workspace SAML app supports SP-initiated and IdP-initiated SSO for the root profile (RPID empty) and for one multi-IdP profile (RPID set). The RPID is copied from that Google profile's SP Entity ID. Only users in the unit or group that profile is assigned to should be assigned to the Okta app instance that carries that RPID. A wrong value in Okta's company-domain field breaks SAML. Okta also says to set domain-specific service URLs so the user enters a username on Google's page first. One-click SSO setup is marked Early Access; manual setup remains the documented path. — [T2] [Okta SAML 2.0 for Google Workspace](https://saml-doc.okta.com/SAML_Docs/How-to-Enable-SAML-2.0-in-Google-Apps.html), [Okta Google Workspace provisioning](https://help.okta.com/oie/en-us/content/topics/provisioning/google/google-provisioning.htm)
- Okta provisioning is a separate switch from SAML. It is an OAuth grant as a Google admin; Okta recommends a system account rather than a person's admin. Enable the operations you actually want: create users, push profile updates, push passwords, deactivate and reactivate. Deactivate sets the Google user inactive. It does not delete the account, because Google delete removes mail, documents, and other content. Password push still matters with SAML, because IMAP, POP, and some desktop and mobile clients need a Google password. Okta's password policy has to satisfy Google's password rules or the push fails. Each assignment can set the target organizational unit, deactivation behavior, and license. The feature list includes group push, import of existing Google users, and schema discovery. Multi-valued boolean custom attributes are dropped on schema import. A user Okta creates sees Google's first-sign-in introduction. — [T2] [Okta Google Workspace provisioning](https://help.okta.com/oie/en-us/content/topics/provisioning/google/google-provisioning.htm)
- If Okta's API calls fail after the grant, check Security > Access and data control > API controls. Services set to Restricted are invisible to an app left at Limited. Trusted lets Okta request all Google data; Limited is what Okta calls the tighter choice. — [T2] [Okta Google Workspace provisioning](https://help.okta.com/oie/en-us/content/topics/provisioning/google/google-provisioning.htm)
- Okta's provisioning guide says Google Workspace does not reuse a username deleted within the past week. Google Admin Help says the address can be reassigned to another managed user during the 20-day window and is removed from Workspace after 20 days. Both are first-party. They were not reconciled in the Directory API reference, which records `deletionTime` and does not state a reuse hold. — [T2] [Okta Google Workspace provisioning](https://help.okta.com/oie/en-us/content/topics/provisioning/google/google-provisioning.htm), [Delete or remove a user](https://support.google.com/a/answer/33314?hl=en) — [T1] [Directory API users](https://developers.google.com/workspace/admin/directory/reference/rest/v1/users)
- When SSO is enabled for the top-level organization, Google 2-Step Verification does not run for users who sign in through that SSO. Post-SSO verification (Security > Authentication > Login challenges) can add risk-based challenges and 2SV after the IdP succeeds. The default differs by profile: other SSO profiles apply those challenges and 2SV; the organization SSO profile bypasses them until you change the policy. Super admins signing in to their administrator accounts use Google, and enrolled super admins complete Google 2SV. Google states that it is enforcing 2SV on administrator accounts; the details page for that enforcement was not read. — [T2] [How 2-Step Verification works with third-party IdPs](https://support.google.com/a/answer/9464354?hl=en), [Login challenges](https://support.google.com/a/answer/6002699?hl=en)
- 2SV enforcement is Security > Authentication > 2-step verification, on a unit or a configuration group, with the child-unit exception above. "On from date" starts within 24–48 hours of the chosen date. Enforcement that allows any method except text and voice locks out users whose only method is a phone code. User log events attribute `login_challenge_method` = `idv_preregistered_phone` is the documented way to find those users before the change. — [T2] [Deploy 2-Step Verification](https://support.google.com/a/answer/9176657?hl=en), [Configuration groups](https://support.google.com/a/answer/9224126?hl=en)
- Context-Aware Access is gated to Frontline Standard and Frontline Plus; Enterprise Standard and Enterprise Plus; Education Standard and Education Plus; Enterprise Essentials Plus; Cloud Identity Premium. A user without one of those editions ignores a Context-Aware Access policy on their unit or group. Policies apply to end-user app access and do not restrict service-account API access. Web, mobile, and desktop built-in apps are rechecked after access is granted. SAML apps are evaluated at sign-in. Conditions include user, IP range, device policy, device OS, and country, and they can be combined with DLP. — [T2] [Protect your business with Context-Aware Access](https://knowledge.workspace.google.com/admin/security/protect-your-business-with-context-aware-access), [Compare Enterprise editions](https://knowledge.workspace.google.com/admin/getting-started/editions/compare-enterprise-editions)
- On Enterprise Standard and Enterprise Plus together: Vault, Gmail/Drive/Chat DLP, alert center, audit and investigation logs, security dashboard, security investigation tool (search and actions such as suspend or restore user), third-party IdP SSO, Google-as-IdP SAML, Secure LDAP, and endpoint management through the enterprise set once advanced mobile management is enabled. Enterprise Plus adds client-side encryption, S/MIME, advanced data exports, data-region policies per unit or group, and Assured Controls as an add-on. A single data-at-rest region for the whole organization is on both editions. Security-health *monitoring* of 2SV, Drive sharing, and group creation is listed for Plus, which is a different fact from whether the setting exists. — [T2] [Compare Enterprise editions](https://knowledge.workspace.google.com/admin/getting-started/editions/compare-enterprise-editions)
- Sign-in and data tickets are read in logs, not by retrying the password. User log events record login type `Google Password`, `SAML`, `OIDC`, `Exchange`, `Reauth`, or `Unknown`, plus challenge type and whether a second factor was used. Logout events show login type as Google Password even when the sign-in was SAML, OIDC, Exchange, or Reauth. Nearby sources: Drive log events, Groups log events (Groups app) and Groups Enterprise log events (Admin console membership changes), SAML log events, Rules log events (DLP), Admin log events, Context-Aware Access log events. Alert center can open an investigation. A DLP rule emits at most 50 alerts a day; incidents past that cap are still in the investigation tool and the Rules audit log, and alert-center data lags the dashboard. The investigation tool's edition list matches the Context-Aware Access list above. — [T2] [User log events](https://support.google.com/a/answer/4580120?hl=en), [Use the alert center](https://support.google.com/a/answer/9105276?hl=en), [DLP incidents and alerts](https://support.google.com/a/answer/9656995?hl=en), [Investigation tool data sources](https://support.google.com/a/answer/10289853?hl=en), [Vault log events](https://support.google.com/a/answer/13851268?hl=en)

## Recommendation

On each escalation, walk the four layers before changing a domain-wide SSO profile or a Drive sharing default: Okta assignment (domain, RPID, provisioning result, API controls), the user's effective SSO profile, license plus suspended/archived/deleted, then the service policy that won (Users view on that setting, and for Drive the shared drive's own unit, managers, and DLP or trust rules). Keep a super admin that can open `admin.google.com` with a Google password and Google 2SV, and treat Okta deactivation as a suspend-style inactive state.

The tradeoff is a slower first action versus a wide SSO, license, or sharing change that the next ticket has to undo. The pages that describe these controls also say several of them can take up to 24 hours, so a second change made "because the first did nothing" is a common way to stack overrides.

## Ruled out

- Entra-style "add a group and the policy updates" as the Workspace model. Units are the base, one per user; groups override only where Google says they do, and access groups can turn a service on only.
- Okta group push as a configuration group. Push can create membership. Configuration still has to be applied in the Admin console, and a group born in the Google Groups app is ineligible.
- Okta deactivation as a Google delete. Okta's own provisioning guide says delete is destructive and that Okta sets the user inactive instead.
- The Enterprise Plus security-health checklist as proof that a control is missing on Enterprise Standard. The comparison page lists monitoring of 2SV and Drive sharing under Plus, and lists the controls themselves on both.
- Google Cloud Directory Sync as the Okta integration. It is a separate way to create groups that are eligible as configuration groups. Okta's documented path is the Workspace app's OAuth provisioning and SAML.
- The Okta Support article on G Suite network masks. Google's legacy SSO page already states the mask behavior, so the support article was not used as evidence.
- `workspace.google.com` marketing and pricing pages. They were returned in search and were not used for control behavior.
- The Drive API permissions schema. It was not fetched. Shared-drive role behavior here is from Admin Help and the Learning Center, which already disagree on folder moves.
- The Admin SDK "Manage user accounts" guide. It was retrieved and added nothing beyond the user and org-unit resources already cited.

## Open questions

- Username reuse after delete. Okta says Google will not reuse a username deleted within the past week. Admin Help says a managed reassignment is allowed during the 20-day restore window. The Directory API reference does not state a hold. Which path Okta's create hits was not tested, and a live create would be a write.
- Folder-move roles. Admin Help and the Learning Center disagree, as recorded above. No Drive API reference was read to break the tie.
- Post-SSO 2SV defaults talk about "the SSO profile for your organization" versus "other SSO profiles." Okta's RPID field selects root versus one multi-IdP profile. The pages read do not map those names onto each other.
- Google's admin 2SV enforcement is announced from the IdP 2SV page. That details page was not read.
- Sign-out is documented as a landing-page URL. The pages read do not say whether leaving that URL ends the Google session, the Okta session, or both.
- "Up to 24 hours" is the published bound for SSO assignment, configuration groups, license auto-assign, and address reassignment. No tighter bound was stated. User restore can take up to 5 days.
- No customer SKU, legacy-versus-new SSO profile, or Okta org wiring was assumed. Which of the two SSO stacks a tenant is on changes the super-admin and network-mask behavior, and that fact is in the tenant, not in these docs.
