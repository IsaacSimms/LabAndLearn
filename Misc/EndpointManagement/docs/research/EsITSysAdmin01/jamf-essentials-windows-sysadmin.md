# What must a systems administrator with strong Intune/SCCM experience know about Jamf (concepts, architecture, core objects, policies, smart groups, prestage enrollment, packages/scripts, inventory, and common troubleshooting patterns) to handle Mac endpoint escalation effectively?

## Answer

The Jamf Pro 11.33.0 documentation set does not define Intune or SCCM equivalents. Handle a Mac as two channels: Apple MDM and declarative device management for enrollment, configuration profiles, and remote commands, and the Jamf management framework (`jamf` binary) for computer policies that install packages, run scripts, and submit inventory. On an escalation, separate a 15-minute policy check-in from inventory and from MDM command history, then read scope (targets, limitations, exclusions, smart-group criteria) and the policy log before changing anything.

## Findings

- Jamf Pro enrolls, configures, secures, and manages Mac computers and Apple mobile devices on Apple's MDM framework and declarative device management protocol. — [T2] Jamf Pro Documentation 11.33.0, About This Guide (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Jamf_Pro_Documentation)
- Jamf Now is a different product: cloud MDM aimed at small and medium organizations, with no public API. Jamf Now also cannot fully manage a directory-bound Mac and points that case to Jamf Pro. — [T2] About Jamf Now (https://learn.jamf.com/r/en-US/jamf-now-documentation/About_Jamf_Now); [T2] Mac Management Considerations (https://learn.jamf.com/r/en-US/jamf-now-documentation/Mac_Management_Considerations)
- Frequently used Jamf Pro objects are configuration profiles (`.mobileconfig`), extension attributes, Mac Apps (volume, App Store, or Jamf App Catalog), packages (Apple installer PKGs and DMGs), patch policies, policies, and smart groups. Policies are computer task sequences run by the Jamf management framework. — [T2] Jamf Pro Objects (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Jamf_Pro_Objects)
- Enrollment submits inventory and establishes management. Automated Device Enrollment is the zero-touch method for organization-owned devices and the only method that can prevent removal of the MDM profile. Device Enrollment is manual, for institutional devices that are not eligible for Automated Device Enrollment. Account-driven User Enrollment is for personally owned devices, leaves them unsupervised, and separates personal and institutional data. Profile-driven User Enrollment is deprecated. — [T2] Enrollment (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Enrollment_into_Jamf_MDM)
- Profile-driven Device Enrollment downloads an MDM profile and reaches User Approved MDM. Computers with macOS 11 or later are supervised after Device Enrollment. — [T2] Device Enrollment for Computers (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Device_Enrollment_for_Computers)
- A Computer PreStage enrollment is the payload set applied during Automated Device Enrollment. Commonly recommended General settings, which the docs say may not fit every environment, are automatically assign new devices, make the MDM profile mandatory, prevent users from removing the MDM profile, and prevent Activation Lock. — [T2] Computer PreStage Enrollment Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Computer_PreStage_Enrollment_Payload_Reference)
- PreStage Account Settings can create the managed local administrator during Setup Assistant. macOS requires that account when Setup Assistant skips user creation or makes the first account a standard user. — [T2] Computer PreStage Enrollment Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Computer_PreStage_Enrollment_Payload_Reference)
- Profiles added to a PreStage must already exist, and their scope must include the PreStage's computers. Put only enrollment-essential profiles there; too many early in Setup Assistant can break enrollment. Payload variables are not substituted at PreStage time. Jamf names Jamf Connect and Platform SSO as examples that belong here because they affect account creation before Setup Assistant continues. On Jamf Cloud, leave the PreStage Certificates payload unset; Jamf manages the TLS certificate. That payload is for an on-premise server whose certificate Apple does not already trust. — [T2] Computer PreStage Enrollment Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Computer_PreStage_Enrollment_Payload_Reference)
- PreStage enrollment packages install during Setup Assistant, before it completes. They must be signed, flat, distribution-style `.pkg` files, trusted by the Mac at enrollment time, and they install in list order. Large packages lengthen enrollment. Jamf's guidance is to keep only enrollment-essential packages here and deploy the rest with a policy after enrollment. A Jamf Cloud distribution point meets the hosting requirements. — [T2] Computer PreStage Enrollment Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Computer_PreStage_Enrollment_Payload_Reference); [T2] Installing Packages During Automated Device Enrollment (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Installing_Packages_during_Automated_Device_Enrollment)
- A policy has tasks, an execution frequency, a trigger, and a scope. It can also be offered in Self Service. The built-in "Update Inventory" policy submits inventory once a week by default; Jamf recommends leaving it enabled. Removing a target from scope leaves settings that policy already applied. — [T2] Policies (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Policies)
- A policy runs on the next check-in of an in-scope computer that also meets the General payload criteria. — [T2] Creating a Policy (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Creating_a_Policy)
- Documented triggers are Startup (startup script must be enabled under Computer Management check-in settings), Login (login hooks must be enabled there), Network State Change (network, computer name, or IP change), Enrollment Complete (immediately after enrollment), Recurring Check-In, and Custom (`jamf policy -event`, with `beaconStateChange` for an iBeacon region change). — [T2] Triggers for Policies (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Triggers_for_Policies)
- The same documentation set, on the manual-run page, also lists Logout (`logout`) as a pre-defined trigger. The trigger reference page does not. Both pages are Jamf Pro Documentation 11.33.0. No product schema was read, so neither page wins. — [T2] Manually Running a Policy (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Manually_Running_a_Policy); [T2] Triggers for Policies (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Triggers_for_Policies)
- Execution frequencies are Once per computer, Once per user per computer, Once per user, Once every day (no log in 24 hours), Once every week (168 hours), Once every month (720 hours), and Ongoing. A Once per computer policy does not run again while a log entry exists for that computer; flush the log to allow another run. Automatic retry on failure (up to 10) exists only for Once per computer. Offline availability exists only for Ongoing. Ongoing plus Recurring Check-In runs on every check-in and can load the server and the Mac. — [T2] Execution Frequency for Policies (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Execution_Frequency_for_Policies)
- The General payload can disable a policy without deleting it, place it in a site and a category, set server-side limits in UTC (including an expiration), and set client-side limits in each Mac's time zone (including day-of-week). — [T2] Policy Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Policy_Payload_Reference)
- The Packages payload can install, cache, install cached packages, or uninstall, and it chooses the distribution point. Built-in uninstall works only for software indexed with Jamf Admin. Jamf Admin was removed in Jamf Pro 11.7; packages uploaded or changed after that upgrade need a vendor uninstaller or a script. — [T2] Policy Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Policy_Payload_Reference)
- Other policy payloads that show up on escalations: Scripts (order relative to other tasks, plus parameter values), Local Accounts (create, delete, reset passwords), Management Account (rotate that account's password), Directory Bindings, Maintenance (update inventory, reset computer names, install all cached packages), Files and Processes (search, kill, delete, or execute a command), and Microsoft Device Compliance (register the Mac with Microsoft Entra; the user must launch Company Portal from Self Service). — [T2] Policy Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Policy_Payload_Reference)
- Scripts live in Jamf Pro before a policy runs them. Parameter labels document values such as `$4`. An operating-system requirement makes Jamf skip the script on incompatible Macs. Priority can place the script after other work in the same policy, such as creating a local account first. — [T2] Scripts (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Scripts)
- Recurring check-in is how often computers ask Jamf Pro for policies. The default is every 15 minutes. Each Mac starts that interval when the setting is applied, so check-in times differ across the fleet. The setting is under Settings, Computer management, Check-in. — [T2] Recurring Check-in Frequency (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Recurring_Check-in_Frequency); [T2] Configuring the Recurring Check-in Frequency (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Configuring_the_Recurring_Check-in_Frequency)
- With local access or SSH, `sudo jamf policy -id <id> -verbose` runs one in-scope policy. The id is the `id` query parameter on the policy URL. `sudo jamf policy` runs Recurring Check-in policies. `sudo jamf policy -event <trigger>` runs policies for that trigger. A custom trigger runs only through the binary. The command fails when the Mac is out of scope. — [T2] Manually Running a Policy (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Manually_Running_a_Policy)
- Policy logs record time, status, and actions per computer. Output is truncated at 25 KB. Flush clears one computer or every computer for that policy. — [T2] Viewing and Flushing Logs for a Policy (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Viewing_and_Flushing_Logs_for_a_Policy)
- Scope can use individual computers, devices, or users; groups; departments; buildings; directory or local users; directory user groups; network segments; and, for some objects, classes or iBeacon regions. Many directory groups in one scope can hurt server performance; Jamf's alternative is a smart group that holds those criteria. — [T2] Scope (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Scope)
- Targets are additive: choosing All Computers and Specific Users scopes both. Limitations narrow a task to users, network segments, or an iBeacon region. Exclusions remove computers, devices, groups, buildings, departments, users, user groups, network segments, or iBeacon regions. For LDAP limitations and exclusions, Jamf matches the user logged in at the Mac, and does not use the computer's User and Location record. — [T2] Adding Targets (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Adding_Targets); [T2] Adding Limitations (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Adding_Limitations); [T2] Adding Exclusions (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Adding_Exclusions)
- Smart group membership updates from inventory criteria. Jamf wants smart groups used for scoping and deployment, and advanced searches used for reports. For two criteria about the same item (apps, certificates, or profiles), list the name criterion first; the reverse can match two different items and widen the group. Nested smart groups, and two groups that depend on each other, are a documented server-performance problem. — [T2] Smart Groups (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Smart_Groups)
- Static groups have fixed membership that an admin changes by hand. A computer joins at its next check-in. — [T2] Static Groups (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Static_Groups); [T2] Creating a Static Group (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Creating_a_Static_Group)
- Computer inventory is collected three ways: the Jamf management framework on the Mac, MDM commands that typically follow those framework inventory commands (visible under the computer's History, Management History), and the declarative status channel, which reports some changes on its own (the documented example is a new macOS version immediately after the update). `jamf recon` in Terminal submits inventory from that Mac. — [T2] Computer Inventory Information (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Computer_Inventory_Information)
- Extension attributes are extra inventory fields for computers, devices, or users, and they are valid smart-group criteria inputs via the inventory references. — [T2] Jamf Pro Objects (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Jamf_Pro_Objects)
- Computer configuration profiles are `.mobileconfig` files, built in Jamf Pro or uploaded, applied at computer level or user level. User-level profiles can wait until the MDM-enabled user logs out and back in, or until restart. Distribution is automatic or Self Service. — [T2] Computer Configuration Profiles (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Computer_Configuration_Profiles)
- Remote commands require a push certificate plus certificate-based authentication and push notifications. They run the next time the computer checks in. History, Management History shows completed, pending, and failed commands. Pending commands can be cancelled. A failed command returns to pending after four hours, then retries at increasing intervals up to one hour. — [T2] Sending a Remote Command to a Computer (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Sending_a_Remote_Command_to_a_Computer)
- Send Blank Push contacts APNs and the declarative status channel so the Mac checks in for work such as installing a configuration profile. — [T2] Remote Commands for Computers (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Remote_Commands_for_Computers)
- Remove MDM Profile removes the MDM profile and configuration profiles Jamf distributed. Jamf can no longer send commands, deploy profiles, or deploy settings that depend on APNs. If the Jamf management framework remains, the Mac is partially managed: inventory, policies, and restricted software continue. — [T2] Remote Commands for Computers (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Remote_Commands_for_Computers)
- Renew MDM Profile renews the MDM profile and the device identity certificate. That certificate's default lifetime is two years. Renewal happens at the next computer check-in. Jamf also issues this command when the built-in CA is renewed. — [T2] Remote Commands for Computers (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Remote_Commands_for_Computers)
- Wipe Computer sends `EraseDevice`, removes the MDM profile, the management framework, and settings and apps Jamf installed, and leaves the computer record and its inventory in Jamf Pro. On supported Macs with macOS 12.0.1 or later, Jamf first attempts Erase All Content and Settings. — [T2] Remote Commands for Computers (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Remote_Commands_for_Computers)
- For Apple silicon, a bootstrap token escrowed to Jamf Pro is required for the `RestartDevice` MDM command and for installing an OS update without user interaction. The Download/Download and Install Updates command applies to Macs that are supervised or enrolled with a PreStage. Apple removed support for software update commands on macOS 27; Jamf's documented path for those Macs is blueprints, which use declarative device management. — [T2] Remote Commands for Computers (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Remote_Commands_for_Computers); [T2] Policy Payload Reference (https://learn.jamf.com/r/en-US/jamf-pro-documentation-current/Policy_Payload_Reference)

## Recommendation

On a Mac escalation, open the computer record and split the channels before editing any object: Management History for pending, failed, or completed MDM commands; the policy log for status and whether a one-time frequency is blocked; scope targets, limitations, and exclusions, including whether an LDAP limit matches the logged-in user; then the smart group's criteria order. Use `jamf policy -id` or `jamf recon` only after that, and only with a session on the Mac. The tradeoff is a slower first response than treating the console like Intune or Configuration Manager. That slower pass is the one the 11.33.0 docs support, because scope removal leaves policy-applied settings in place, a log entry suppresses Once per computer, and an MDM command can sit pending while the binary is still checking in.

## Open questions

- Whether a computer configuration profile is removed when a Mac leaves scope. The profile page that was read describes level and distribution only. The policy page does say scope removal leaves policy-applied settings in place. Those are different objects, and the profile side is unresolved.
- Logout as a trigger. The trigger reference omits it; the manual-run page includes `logout`.
- Once per computer: a log entry blocks another run until flush, and the same paragraph offers up to 10 automatic retries after failure. The docs do not say whether a failed log blocks those retries.
- When smart-group membership recalculates. The page says membership is dynamic from inventory criteria and does not give the schedule.
- The remote-command page says a command runs at the next check-in and does not say whether that is the 15-minute policy check-in or an APNs-driven MDM check-in. Send Blank Push is the documented way to prompt a check-in for a profile install.
- How devices are assigned into a PreStage from Apple Business Manager or Apple School Manager. The payload reference describes the enrollment payload, not the device-assignment flow. The editor article 404'd.
- Site scoping rules. The policy General payload can put a policy in a site; site visibility was not read.
- Reserved script parameters `$1` through `$3`. The Scripts page documents labels and uses `$4` as an example only.
- Component paths and launch daemons for the Jamf management framework. Inventory says the framework is on every enrolled Mac and points to Applications and Utilities, which was not read.
